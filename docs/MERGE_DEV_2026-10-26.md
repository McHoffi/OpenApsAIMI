## Translation loss and repair

The first merge pass took upstream's translation files, and it dropped the fork's own translations.
Reported by the user on 2026-10-26.

- Found: `core/ui` German went from 812 to 427 strings. French lost 105 in `plugins/main` and 50 in `app`.
- Repair 1 (`26cc2dcf49`): for every changed translation file, every string that was in the
  pre-merge file, is missing now, and still exists in the English file was put back. 594 strings.
- Repair 2 (`548acc8a1b`): 34 German strings for Settings → General and Appearance (units, language,
  simple mode, glass look, Vico chart, colour scheme). They had no German text before the merge either.
- Repair 3 (`de8830f15f`): 789 German strings from the fork history (every 15th first-parent commit)
  that exist in English and had no German entry. Mostly `core/keys`, `core/ui`, `plugins/aps`, `plugins/main`.
- Only German and English are kept up to date, as the user asked. Other languages were fixed only by
  repair 1. They may still miss fork strings.
- A restored German text can be old if the English text changed later.
- About 7600 English strings exist. About 3700 have a German name now. The rest stays English.

**Lesson for the next merge:** never take `--theirs` for a `values-xx/strings.xml` file. Merge by key
instead: keep upstream's text, and keep the fork's keys that upstream does not have. Compare the string
count of each translation file before and after the merge.

## Found on the device after the merge: AAPS folder and Closed Loop

The user saw "Developer version, Closed Loop is not available" and many `extra (1)`, `extra (2)` folders.
The merge did not change this code (`FileListProviderImpl`, `ConfigImpl`, folder picker are the same
before and after). Cause, read from `adb logcat`:

- Dev builds allow Closed Loop only if the file `extra/engineering_mode` is found. AAPS looked for it
  only through the folder chosen in the Android folder picker.
- On this phone (Xiaomi, HyperOS 3, Android 16) the system `ExternalStorageProvider` fails with
  `NoSuchFileException: /storage/emulated` in `isRestrictedPath`. The picker shows no internal storage,
  and `listFiles()` on the chosen folder returns nothing. Because of that `ensure…DirExists()` did not
  see the existing `extra` folder and made a new one each time (`extra (1)` …).
- AAPS used the chosen folder (here `/storage/emulated/0/AAPS`), AIMI always used `Documents/AAPS`.
  Two base folders.

Fix (`0fbc761185`, `e26cab9d28`):

- With "all files access", `FileListProviderImpl.baseDir()` is `Documents/AAPS` as plain files. Without
  it the chosen folder is used as before.
- The chosen folder is copied into `Documents/AAPS` once (`preferences`, `exports`, `temp`, `extra`,
  no overwrite). Marker file: `.chosen_folder_copied`. The old folder is left as it is.
- A sub folder that Android renamed on creation is deleted again, so no copies pile up.
- `Config.isEnabled` reads option files (`engineering_mode` …) as plain files first.
- Maintenance shows `Documents/AAPS`. A tap shows a message that the folder cannot be changed.
- Libre3 and Dexcom ONE+ availability accept the fixed folder when no URI is stored.
- New test: `ConfigImplOptionsTest`.

Not done: `AimiBackupManager` and `AimiStorageHelper` still read the chosen folder URI for their
backups. The import of an old backup was not tested.
